## Why

`SearchableItem.expected_product_line`/`expected_category` (added by the archived `item-category-relevance-filter` change) store a flat, string-deduplicated list. When two vendors happen to report the identical raw value, the single-item edit form's vendor-labeled suggestion checkboxes both pre-check regardless of which one the operator actually opted into — and unchecking just one of the two identically-valued checkboxes is a silent no-op, since both checkboxes submit the same string and the server has no way to tell which one was toggled. This is a real, currently-untested bug in a shipped capability (surfaced during `/opsx:explore` while designing `bulk-item-editing`'s vendor-scoped `expected_*` suggestions), not a hypothetical. It also blocks `bulk-item-editing` from adding a symmetric "remove" control alongside its existing additive-only suggestions, since there is no stored representation of "this value, specifically as claimed via this vendor" for a remove action to target.

## What Changes

- `SearchableItem.expected_product_line`/`expected_category` change from `list[str]` to `list[{"value": str, "source": str | None}]` — each entry records which vendor (`Source.key`) it was claimed through via a suggestion checkbox, or `source: null` for a manually-typed value.
- The single-item edit form (`SearchableItemForm`) is reworked: suggestion checkbox identity, pre-check state, and effective removal all key off the exact `(source, value)` pair rather than the bare value string.
- A manually-entered value renders as its own row inline alongside vendor-sourced suggestion rows, labeled with a fixed "Manual entry" signpost, rather than living in a separate free-text textarea block — this is how a value with no vendor provenance is distinguished from one claimed through a specific vendor's suggestion.
- Checking two different vendors' suggestion checkboxes for the same raw string now stores two distinct entries (one per vendor) instead of collapsing to one deduplicated string. **BREAKING** relative to `item-category-relevance`'s currently-specced dedup-by-exact-string-equality behavior and its "checking suggestions from two different vendors stores one deduplicated entry" / "re-editing pre-checks every matching vendor's checkbox" scenarios.
- A data migration best-effort-attributes existing plain-string entries to a vendor: per item, per stored value, if the value matches exactly one of the item's currently-configured vendors' `ObservedCategoryValue` rows for that field, the migrated entry is tagged with that vendor; if it matches zero or more than one, it falls back to `source: null` (the honest "we can't tell" case, which is also the universal case — see below).
- **BREAKING**: matching becomes vendor-scoped. `tracking/scrape.py`'s handoff now builds a *per-vendor pruned* value list for each parser instance: a vendor-tagged entry filters only that vendor's own rows; a manually-entered (`source: null`) entry filters every vendor configured for the item, since it was never claimed for one vendor in particular. There is no fallback for a vendor with zero applicable entries — that vendor's rows simply pass through unfiltered on that axis, even when the item has entries tagged for *other* vendors. This explicitly overturns `item-category-relevance-filter` Decision 1 ("an item's category identity doesn't vary by vendor"); `JSONSearchParser.add_result` itself is unchanged code, but what it receives, and therefore what gets filtered, changes. An operator adding a new `ItemSource` to an item that already has vendor-scoped `expected_*` entries must deliberately extend coverage to the new vendor themselves — this is not automatic, and is an accepted trade-off, not a defect (see design.md Decision 2).
- **Explicitly out of scope**: reworking `bulk-item-editing`'s vendor-scoped `expected_*` suggestion UI and apply logic (Sections 4–5 of that change) to build on this corrected model. That work is flagged as a known follow-up in `bulk-item-editing`'s own `design.md` (on its branch) and will be picked up as a separate pass once this change lands.

## Capabilities

### New Capabilities
(none)

### Modified Capabilities
- `item-category-relevance`: the "Item form offers vendor-labeled checkbox suggestions plus manual entry" requirement's storage/dedup/pre-check/removal behavior moves from string-level identity to `(source, value)`-pair-level identity. The matching requirements ("Parser results must match at least one expected product line/category...") are also modified: matching now operates on the per-vendor-pruned subset of an item's entries (that vendor's own tagged entries plus every `source: null` entry), not the full flat list — a genuine behavior change, not just a storage-layer one.

## Impact

- **Models** (`tracking/models.py`): `expected_product_line`/`expected_category` JSONField payload shape changes from `list[str]` to `list[dict]`. `JSONField` itself needs no schema migration, but a **data** migration is required to transform every existing row's stored lists.
- **Forms** (`tracking/forms.py`): `SearchableItemForm`'s suggestion-choice building, pre-check logic, manual-entry handling, and save/merge logic (`_suggestion_choices`, `_merge_and_dedupe`, `_split_stored_values`) are reworked around `(source, value)`-pair identity instead of bare-string identity.
- **Scrape handoff** (`tracking/scrape.py:633-634`): build a per-vendor pruned value list per parser instance (a vendor's own tagged entries plus every `source: null` entry) instead of one flat list per item; `tracking/parsers.py`'s own code is untouched, but the filtering outcome it produces changes.
- **Template** (`tracking/templates/tracking/searchableitem_form.html`): manual entries render as inline rows (labeled "Manual entry") alongside vendor-sourced rows, not in a separate textarea.
- **Tests** (`tracking/tests/test_item_category_relevance.py`): several existing tests assert string-level dedup/pre-check behavior as correct — those are being corrected to match the new, intended behavior, not just extended.
- **No changes** to `tracking/parsers.py`'s matching logic, the `ObservedCategoryValue` model, `tracking/tasks.py`, or any vendor-fetch/parsing code.
- **No changes** to `bulk-item-editing` (a separate, not-yet-archived change on another branch) — its `expected_*` vendor-scoped suggestion rework is deliberately deferred past this change.
