## Context

`view_terms` (`SearchableListView`) already renders a checkbox per active row and a `mode=selected` POST path (`UpdateFromWebView`, `tracking/views.py:894-972`) that turns checked `item_ids` into a scoped price-update dispatch. That plumbing was named in the archived `item-metadata-enrichment` change and in `README.md`'s "Deferred / future directions" section as the reusable groundwork for general bulk-editing, but it was built for a single-purpose, fire-and-forget action (dispatch a background price scrape) — it doesn't need to carry state across multiple requests or express "leave this field unchanged."

Two existing single-item mechanisms are being generalized here without being modified themselves:
- `request_metadata_refresh(item)` (`item-metadata-enrichment`) is the sole entrypoint allowed to enqueue a metadata refresh and to perform the provider-change reset (clear `payload`/`external_id`/`pinned_external_id`, reset `status` to `unfetched`). Bulk-editing `metadata_provider_key` must call this per affected item rather than duplicate its logic.
- `observed_values_for_item(item, field_name)` and the vendor-labeled suggestion-checkbox pattern (`item-category-relevance`) scope `ObservedCategoryValue` lookups to one item's configured `Source`s. Bulk-editing needs the same underlying data source but scoped to the union of vendors across a whole selection, with per-vendor subset counts — a new query shape, not a reuse of the existing function signature.

This design was worked out interactively in `/opsx:explore`; the decisions below restate that conversation's conclusions with rationale.

## Goals / Non-Goals

**Goals:**
- Let an operator change one or more fields (`priority`, `active`, `tags`, `metadata_provider_key`, `expected_product_line`, `expected_category`, and per-`Source` `title_include_patterns`/`title_exclude_patterns`) across an arbitrary selection of existing items in as few selection actions as possible.
- Preserve the selection across multiple sequential partial edits — re-selecting items is the most tedious part of the flow and must not be discarded after a single Apply.
- Reuse `request_metadata_refresh` and `ObservedCategoryValue` as the authoritative mechanisms for their respective concerns, rather than reimplementing them at bulk scope.
- Apply best-effort, per-item: one item's failure must not prevent the rest of the selection from being attempted in the same round.
- For every addable/removable per-row value (a tag, a vendor-scoped expected value, a manual expected value), let the operator see at a glance how many of the current selection already have it, and set exactly one of add/remove/leave-unchanged for it through a single unambiguous control (Decision 9).

**Non-Goals:**
- Bulk-editing `text` — no sensible shared value exists across an arbitrary selection.
- **Creating brand-new** manual `expected_product_line`/`expected_category` values via free text in bulk mode — v1 offers the tri-state add/remove/unchanged control (Decision 9) only for manual values *already present* somewhere in the selection; bulk-authoring values no selected item has yet (e.g. a textarea) remains deferred, revisit based on usage friction. **This Non-Goal does not extend to include/exclude search patterns** — Decision 10 deliberately offers free-text bulk authoring there, for reasons specific to that field (patterns have no observed-value fallback the way `expected_*` does via `ObservedCategoryValue`).
- An audit/undo log of bulk changes — no existing precedent in this app (`WebUpdate`/`FetchJob` are fetch-job history, not field-edit history).
- A periodic or scheduled bulk operation — this is an operator-triggered, synchronous-apply feature only.
- Handling concurrent mutation of a selected item by another user or process mid-session (see Risks below) — multi-user interaction in general is a future concern for this app, not solved here.

## Decisions

### 1. The workspace is a persistent, multi-round session, not a one-shot form

A single POST-then-redirect form (mirroring `BulkAddItemsForm`) was considered and rejected: it would force the operator back to `view_terms` and through re-selection for every additional field they want to change, which is exactly the friction this feature exists to remove. Instead, `BulkEditItemsView` renders a workspace that survives repeated Apply rounds against the same working selection, only returning to `view_terms` on an explicit "Done" action.

### 2. Working selection carried as hidden POST fields, not a URL or server-side token

Three options were considered for carrying the working `item_ids` set across the initial POST from `view_terms` and every subsequent Apply:
- **GET query string + redirect** (standard Post/Redirect/Get): refresh-safe and bookmarkable, but `view_terms`' "select all" has no cap and `BULK_ADD_MAX_TERMS = 200` already signals the scale this app expects for batches — a few hundred integer ids risks an unwieldy URL with no guaranteed safe limit.
- **Server-side token** (session or a short-lived DB row keyed by an opaque id in the URL): avoids both the URL-length and refresh-resubmit problems, but introduces new server-side state with no existing precedent in this app (no session-backed workflow exists today) — expiry policy and concurrent-tab handling would be new infrastructure for a feature that doesn't otherwise need it.
- **Hidden POST fields, re-rendering the same view on each Apply** (chosen): no URL-length risk at any selection size, no new server-side state. Trade-off: the workspace page is not a plain idempotent GET, so a manual browser refresh mid-session prompts to resubmit the last Apply.

The trade-off is accepted because nearly every field operation here is naturally idempotent — `priority`/`active` overwrite to the same value harmlessly, tag add/remove and the `expected_*` suggestion apply are dedup-safe by construction. The one non-idempotent case, `metadata_provider_key`, would at worst produce a redundant `request_metadata_refresh` enqueue on an accidental resubmit — wasteful, not harmful, since the existing bounded-rate drain queue already absorbs large batches of enqueues from bulk creation today.

### 3. Every field defaults to "leave unchanged" — a real sentinel, not a blank/false value

Neither existing form in this codebase needs this: `SearchableItemForm` and `BulkAddItemsForm` both bind every field to a concrete value on every save. A bulk-edit round, by contrast, is usually a partial edit — the operator wants to change one or two fields and leave the rest of the selection's existing values alone. Each field therefore needs a tri-state-or-wider choice (e.g. `active`: leave / activate / deactivate; `metadata_provider_key`: leave / set-to-X / clear) rather than reusing the single-item field's natural blank/false default, which would otherwise be indistinguishable from "clear this."

This sentinel is what makes the multi-round workspace (Decision 1) safe to use repeatedly: an Apply round only ever touches the fields explicitly set away from "leave unchanged," so an earlier round's changes are never at risk of being silently reverted by a later, unrelated round.

### 4. `tags` and `expected_product_line`/`expected_category` are additive/subtractive, never a full replace

A single shared field value cannot safely overwrite every selected item's whole `tags` or `expected_*` list — each item likely carries pre-existing values (other tags, manually-curated `expected_*` entries) unrelated to the current bulk intent, and a full replace would silently destroy them. `tags` therefore exposes two independent sets (add / remove); `expected_product_line`/`expected_category` are add-only, merged and deduplicated by exact string equality into each affected item's existing list — the same dedup rule `item-category-relevance`'s single-item form already uses.

### 5. `expected_product_line`/`expected_category` suggestions are vendor-scoped across the selection, and apply only to the matching subset

`item-category-relevance`'s `observed_values_for_item(item, field_name)` scopes to one item's configured `Source`s. Bulk editing needs the union of vendors across every selected item instead: for each `Source` present via `ItemSource` on at least one selected item (no minimum-shared threshold — even a vendor used by just one of N selected items gets its own labeled group, e.g. "1 of 20"), a suggestion checkbox group is built from `ObservedCategoryValue` scoped to that vendor. On Apply, each checked `(vendor, value)` pair is added only to the items in the working selection that have that vendor's `ItemSource` configured — items without that vendor are unaffected by that specific checkbox, and this is stated plainly in the UI next to each group's label.

This requires the checkbox's submitted value to carry `(vendor, value)`, not just the raw string the single-item form uses — the single-item form can get away with a bare string because it only ever reconciles against one item's list; the bulk form must know which vendor each checked value came from in order to compute the correct subset at apply time.

**Alternative considered**: only show vendor groups shared by two or more selected items (a "genuinely bulk" threshold). Rejected — the per-group count already communicates scope honestly ("1 of 20"), and filtering out singleton vendors would silently hide a suggestion an operator might still want, for no real complexity savings.

### 6. `metadata_provider_key` routes through the existing entrypoint, per item

Bulk-setting or bulk-clearing `metadata_provider_key` calls `request_metadata_refresh` once per affected item, exactly as `BulkAddItemsView` and `SearchableUpdateView` already do. The provider-change reset (clearing stale `payload`/`external_id`/`pinned_external_id`, resetting `status` to `unfetched`) lives entirely inside that entrypoint's call graph already, so bulk-edit gains it for free rather than needing its own copy. This also means a bulk-set across many items enqueues many `MetadataFetchRequest` rows at once, which the existing bounded-per-wake periodic drain already handles identically to a large bulk-add batch — no new queueing concern.

### 7. Per-item best-effort apply; errors reported per item, not aggregated

Each Apply round attempts every item in the current working selection independently for whatever fields changed that round. An item-level failure (e.g. a save/validation error) is recorded against that item and does not prevent the remaining items from being attempted. The round's summary message reports success/failure per item rather than a single pass/fail for the whole batch — consistent with the workspace's overall philosophy of never discarding progress on the rest of the selection because of one item.

### 8. Per-row "remove from selection" instead of forcing a return to `view_terms`

Since the roster panel already lists every selected item (text, active badge, tags, priority) as part of showing what a round will affect, a lightweight per-row removal action costs little to add and avoids sending the operator back through `view_terms`'s full checkbox re-selection over a single mis-included item. It operates purely on the working `item_ids` carried in the form — no new server-side state.

### 9. Tags and `expected_product_line`/`expected_category` use one tri-state add/remove/unchanged control per row, not independent multi-selects/checkboxes

Reopens `tags_add`/`tags_remove` (Decision 4) and the vendor-scoped `expected_*` suggestion checkboxes (Decision 5), now that `expected-value-vendor-provenance`'s landed `(value, source)`-pair storage (see "Known Follow-up" above) finally makes a well-defined remove action for `expected_*` possible — the exact gap that blocked adding one the first time this was explored. Worked out interactively in `/opsx:explore`, 2026-08-23.

**Problem with the current mechanism.** `tags_add`/`tags_remove` are two independent `ModelMultipleChoiceField`s (`SelectMultiple` widgets), both drawing from the same `Tag.objects.all()` queryset — nothing stops an operator from selecting the same tag in both, an operator has to scan two separate list boxes to find one tag's current intent, and there is no way to see, per tag, how many of the current selection already have it. `expected_product_line_suggestions`/`expected_category_suggestions` are additive-only checkboxes with the same missing-context problem, plus no remove action at all.

**Chosen mechanism: one radio-style tri-state control per row.** Each row — a `Tag`, a vendor-scoped `(source, value)` suggestion, or a manual `(None, value)` entry — gets exactly one HTML radio group of three options: add / remove / unchanged, defaulting to unchanged. Radios natively guarantee "exactly one selected," so the mutual-exclusivity constraint needs no JavaScript and no custom validation beyond what `forms.ChoiceField` already provides. Each row's radio group needs its own `name` (HTML radios only group by shared `name`), so rows are name-spaced `<field>_state:<row_key>` — `tag_state:<tag.pk>` for tags, `expected_product_line_state:<encoded>` / `expected_category_state:<encoded>` for expected-value rows, reusing the existing `json.dumps([source_key, value])` encoding `_bulk_edit_suggestion_choice_value` already established (Decision 5) rather than inventing a second scheme; a manual row's `source_key` is `None`, which round-trips through that encoding as JSON `null` with no special-casing needed. Each control renders as three Bootstrap toggle buttons — `<input class="btn-check">` + sibling `<label class="btn btn-outline-*">`, already this app's styling idiom via `_apply_bootstrap_form_classes` — labeled `+`/`−`/`o`; the active-state highlight is pure `:checked` CSS, not a JS behavior.

Alternatives considered and rejected:
- **Two independent multi-selects generalized to expected_* (mirroring today's tags mechanism), with add/remove sets kept separate per field.** Rejected — doesn't fix the actual complaint (an operator can't see one row's state at a glance, and nothing prevents contradictory add+remove selections on the same value); it would just be more of what's already wrong.
- **A single hidden field per row-family, mutated by client-side JS on button click.** Rejected — reimplements what native radios already do declaratively, adds a JS dependency this form doesn't otherwise have, and breaks plain-HTML-form submission as a fallback.
- **A Django `formset` (one sub-form per row).** Considered since `ItemSourceFormSet` already exists in this codebase for a similar "N rows of the same shape" problem — rejected here because formsets model a variable, client-managed row count (add/delete rows in the browser) via a management form, whereas both row universes here (all `Tag`s; all suggestion/manual rows for the selection) are fully server-computed and fixed for a given render. N dynamically-named plain `ChoiceField`s added in `__init__` is simpler and avoids formset machinery this use case doesn't need.

**Row universe differs by field, deliberately.** Tags keep today's full `Tag.objects.all()` universe — every tag in the system gets a row, even one no selected item currently has — because that preserves the real capability of bulk-adding a tag to a selection for the first time (e.g. tagging a fresh batch "clearance"). Expected-value vendor-suggestion rows stay scoped as Decision 5 already established (every vendor present on ≥1 selected item, sourced from `ObservedCategoryValue`) — unchanged. **New**: a "Manual entry" group is added, sourced not from `ObservedCategoryValue` but from the union of `source: null` entries already present across the working selection's `expected_product_line`/`expected_category` — one row per distinct manual value. A manual row can never have a 0-item count by construction (it only exists because ≥1 selected item already has it), unlike a tag row or a vendor-suggestion row, both of which can legitimately show 0 (that's what "add" exists to change).

**The per-row "Active on N items in current selection" annotation is new, not a relabeling of an existing number.** For tags, this needs a new batched `Count`-over-selection query (same shape `vendor_scoped_suggestions_for_items` already uses for vendor/item-count). For expected-value rows, it is *not* the existing vendor-group-level `item_count` ("N of M selected items have this vendor configured") — that number stays exactly where it is, as the group heading, because it still answers a different, still-useful question (can "add" possibly do anything for this vendor). The new number answers "how many selected items already have this exact `(value, source)` entry stored" — since `expected_product_line`/`expected_category` are `JSONField` lists of dicts, this isn't portably SQL-aggregable across this app's supported backends (SQLite, Postgres), so it's computed by fetching each selected item's stored list once (one query, bounded by selection size, not per-row) and tallying in Python — the same pass that also builds the "Manual entry" group's rows and per-row counts, since both need the same raw data. The annotation is shown only when the count is ≥ 1, per the original ask; a 0-count vendor-suggestion or tag row shows no annotation line at all.

**Removal for `expected_*` is now well-defined, closing the original gap.** A row set to "remove" strips the exact `(value, source)` pair from every selected item that currently has it — vendor-scoped rows only from items with that vendor's `ItemSource` configured (mirroring add's existing subset semantics from Decision 5); manual rows from every selected item that has that manual entry, since a manual entry was never vendor-scoped to begin with. This needs a `_remove_expected_entries` helper, sibling to the existing `_merge_expected_entries` (task 5.6), filtering by `(value, source)` inequality rather than merging.

**Idempotence carries through by construction, not by new logic.** Add-to-an-item-that-already-has-it and remove-from-an-item-that-doesn't are no-ops: tags via Django's ordinary M2M `add()`/`remove()` semantics (already true today); expected values via `_merge_expected_entries`'s existing pair-dedup for add, and `_remove_expected_entries`'s pair-equality filter simply not matching anything for remove. No new invariant needs enforcing — the existing mechanisms already guarantee it once each row's state is resolved correctly.

**`active` stays a plain tri-state dropdown, not a per-row control.** It has no row identity to itemize — one global mode for the whole apply round, not one entry among many — so it's a different shape of problem and out of scope for this redesign.

**Mass-adding brand-new manual values remains a non-goal.** The "Manual entry" group only ever surfaces values already present on some selected item; a free-text bulk-add path for values no selected item has yet is still deferred (see Non-Goals). This redesign makes *existing* manual values first-class in bulk-edit; it does not add a manual-entry-creation mechanism.

### 10. Include/exclude search patterns are grouped by Source, tri-state per existing pattern, plus a free-text add path unique to this field

Worked out interactively in `/opsx:explore`, 2026-08-23 (same session as Decision 9). Extends the tri-state mechanism to `ItemSource.title_include_patterns`/`title_exclude_patterns`, the per-`(item, source)` regex lists that gate which scrape results a source's search matches against for that item (edited today, per item, as full-replace textareas in `ItemSourceForm`).

**Structural difference from `expected_*` that shapes this decision.** `expected_*`'s vendor-suggestion rows are sourced from `ObservedCategoryValue`, a system-observed taxonomy independent of what any item currently stores; only its "Manual entry" rows are sourced from values already present on selected items. Include/exclude patterns have no `ObservedCategoryValue` equivalent — nothing observes a regex from scrape results, a pattern only exists because an operator typed it into some item's `ItemSource`. So **every row here is structurally a "manual entry" row**: the candidate universe for a Source's group is the union of patterns already configured on any selected item's `ItemSource` for that Source, not a separately-sourced suggestion list. A second structural difference: `expected_*` mutates a field on `SearchableItem` itself, with `(value, source)` provenance baked into each stored entry so duplicates can be detected across vendors; patterns mutate a field on **`ItemSource`**, a separate per-`(item, source)` row that may not exist for a given item at all. The `(item, source)` foreign key already *is* the provenance — no pair-tagging needed on the stored value, which makes the merge/remove logic simpler than `_merge_expected_entries`/`_remove_expected_entries`, not harder.

**Chosen mechanism: grouped by Source (not by field), union visibility, `Source.name` label.** For every `Source` with at least one `ItemSource` among the working selection (`item_count > 0`), one group renders, labeled with `source.name` (not `source.key` — chosen for readability over matching the `expected_*` groups' key-based label, since this is a new section, not a continuation of an existing labeling convention) and its "N of M selected items configured" count. Each group holds two subsections, Include and Exclude, each listing one tri-state row (design.md Decision 9's control, reused verbatim) per pattern already configured on any selected item's `ItemSource` for that Source and field. Visibility uses **union, no minimum-shared threshold** — mirroring Decision 5's precedent exactly (a Source configured on just 1 of 20 selected items still gets its own group, labeled "1 of 20"); a stricter intersection-only rule was considered and rejected for the same reason Decision 5 already rejected a shared-by-2+ threshold: the count already communicates scope honestly, and hiding a Source an operator might still want to bulk-edit saves no real complexity. When a subsection's row list is empty (the Source has `ItemSource` rows in the selection, but no patterns anywhere for that field), it shows an explicit "No patterns defined" note rather than silently rendering blank — a deliberate departure from how `product_line_groups`/`category_groups` handle an empty group today (no message at all), justified here because each Source group has *two* subsections and a silent-blank one is easy to misread as a rendering gap rather than "genuinely nothing configured yet."

**Apply-time target and subset semantics.** A tri-state row set to add or remove resolves, per Decision 5/9's existing subset rule, only against items in the working selection that have a matching `ItemSource` for that row's Source — items without it are unaffected, satisfying the requirement that bulk pattern edits never implicitly create a new `ItemSource`. Resolution batch-fetches the relevant `ItemSource` rows once per apply round (keyed by `(item_id, source_id)`, mirroring how `tags_by_pk` is looked up once for the whole round rather than per item), mutates each qualifying row's `title_include_patterns`/`title_exclude_patterns` via plain string-list add/filter (`_merge_patterns`/`_remove_patterns` — no pair-dedup needed, per the structural point above), and saves it inside that item's existing per-item `transaction.atomic()` block in `_apply_bulk_edit_to_item`, preserving Decision 7's per-item best-effort semantics.

**New: a free-text manual-add path, deliberately reopening the `expected_*` Non-Goal for this field only.** Each Include/Exclude subsection additionally offers a small (3-row) textarea, one pattern per line, validated with the same per-line `re.compile` check `ItemSourceForm._clean_patterns` already applies. Text typed here is treated as additional "add" values for that `(source, field)`, unioned into the same add-set the tri-state rows feed before the merge step — the textarea is a second *source* of values to add, not a second apply mechanism, so it inherits idempotence for free (retyping an already-present pattern is a no-op via the same string-equality dedup). It is deliberately not offered for `expected_*`: that field almost always has an `ObservedCategoryValue` fallback to suggest from, so free-text authoring there is a nice-to-have the Non-Goals section correctly deferred; patterns have no such fallback, so a Source with zero patterns configured anywhere in the selection would otherwise have a permanently-empty, useless subsection with no way to ever get its first pattern in bulk. The control needs a visual cue distinguishing "this box is additive-only, not a fourth tri-state option" — rendered as the same disabled, permanently-`checked` radio + label markup the tri-state row already uses for its "add" (`+`) state (reusing its existing `:checked`/`.tristate-btn-soft` CSS rather than inventing a `.active`-class-based imitation), placed beside the textarea to signal "whatever is typed here is added to every valid item in this Source" without implying it can be toggled.

**Alternatives considered and rejected:**
- **Group visibility by strict intersection** (a Source's group appears only if every selected item has it configured) — rejected as inconsistent with Decision 5's already-established union precedent, and for the same reason: it would hide a Source used by 19 of 20 items entirely, for no complexity savings.
- **Two top-level sections (Include patterns / Exclude patterns), each grouped by Source** — mirroring how `expected_product_line`/`expected_category` split into two top-level sections. Rejected in favor of Source as the primary grouping, since a Source's include and exclude patterns are two facets of configuring that one Source, and an operator reasoning about "what does this Source match on" benefits from seeing both together.
- **Silent-blank empty subsections**, matching `product_line_groups`/`category_groups`' existing (unannounced) empty-group rendering — rejected per above; the two-subsections-per-group shape makes an unannounced empty subsection more likely to read as missing content than "nothing configured."
- **No free-text add path, mirroring the `expected_*` Non-Goal exactly** — rejected because, unlike `expected_*`, patterns have no suggestion fallback; without free text, a Source with no prior patterns in the selection could never get bulk-added patterns at all, which would make this section far less useful for what's likely the common first-time-configuring-a-batch case.

## Risks / Trade-offs

- **[Risk]** An item in the working selection could be deleted, deactivated, or otherwise mutated by another user or background process between the initial selection and a later Apply round in the same session. This change does not detect or handle that case — multi-user interaction is a broader, unaddressed concern for this app (single-operator tool today), not something to solve here. → **Mitigation**: none implemented; documented explicitly in `tasks.md` and `README.md`'s "Deferred / future directions" as a known limitation to revisit if/when this app gains real multi-user usage.
- **[Trade-off]** Carrying the selection as hidden POST fields (Decision 2) means the workspace page is not refresh-safe in the ordinary browser sense. → Mitigation: accepted because the underlying field operations are idempotent by construction; the one non-idempotent case (metadata refresh enqueue) is merely wasteful, not incorrect, on an accidental resubmit.
- **[Risk]** The vendor-scoped `expected_*` suggestion query (Decision 5) is a new query shape against `ObservedCategoryValue`, run across a potentially large item selection and its vendors — needs to stay a bounded number of queries (mirroring the existing discipline in `SearchableListView.get_queryset`'s eager-loading), not one query per selected item. → Mitigation: implementation must batch the vendor/count computation and the per-vendor suggestion lookup, not loop per item; covered as an explicit task.
- **[Trade-off]** No audit/undo log means a mistaken bulk Apply (e.g. the wrong tag added to 50 items) has no built-in recovery path beyond manually reversing it (e.g. bulk-remove the same tag). → Accepted as proportionate for v1, consistent with this app's existing lack of any edit-history mechanism outside fetch-job records.
- **[Risk]** The free-text pattern-add path (Decision 10) is the first place in bulk-edit where an operator authors a brand-new value rather than choosing among precomputed rows — an invalid regex now has to be validated and reported back per `(source, field)` textarea, on a form whose other fields all fail closed via fixed choices. → Mitigation: reuse `ItemSourceForm._clean_patterns`'s existing per-line `re.compile` validation and error surfacing verbatim, rather than inventing new validation behavior for bulk-edit.
- **[Risk]** `source_pattern_groups_for_items` (Decision 10) is a new query shape against `ItemSource`, and its apply-time counterpart batch-fetches `ItemSource` rows keyed by `(item_id, source_id)` — both need to stay bounded regardless of selection size, matching the discipline already required of `vendor_scoped_suggestions_for_items` and `expected_value_activity_for_items`. → Mitigation: one query for the group/count computation, tallied in Python; one batched fetch at apply time; covered as an explicit task with a query-count test.

## Migration Plan

1. No schema or migration changes — this change is purely new views/forms/templates plus a non-model helper function for vendor-scoped `ObservedCategoryValue` lookup.
2. Ship with the "Bulk Edit Selected" action additive alongside existing `view_terms` actions; no existing behavior (single-item edit, bulk add, price-update selection) is altered except the checkbox-visibility widening, which is backward compatible (widens what can be selected, doesn't change what `mode=selected` price-update does with that selection).
3. No rollback complexity beyond removing the new view/URL/template — no data is migrated or backfilled.

## Known Follow-up

**UPDATE (2026-08-22): the storage-model rework anticipated below has landed.** `expected-value-vendor-provenance` merged from `dev` (archived at `openspec/changes/archive/2026-08-22-expected-value-vendor-provenance/`) and moved `SearchableItem.expected_product_line`/`expected_category` from `list[str]` to `list[{"value": str, "source": str | None}]`, exactly as this section predicted, including a migration (`0022_expected_value_vendor_provenance.py`) that converts every existing item's stored values to the dict shape. This was discovered by merging `dev` into `bulk-item-editing` and diffing the result (`/opsx:explore`, 2026-08-22) — not by revisiting this section proactively.

**This is now a confirmed defect in the merged code, not a future consideration.** `tracking/forms.py`'s bulk-edit apply path was never updated for the new shape:

- `_apply_bulk_edit_to_item` merges `expected_product_line_add`/`expected_category_add` into the item's existing list via `dict.fromkeys([*item.expected_product_line, *...])`, which assumes both sides are flat strings. Against the landed model, `item.expected_product_line` is a list of dicts — dicts aren't hashable, so this raises `TypeError: unhashable type: 'dict'` for any selected item that already has stored entries. `apply_bulk_edit`'s per-item try/except catches it, so it degrades to a reported per-item failure rather than a crash, but the field silently fails to update.
- For an item with no pre-existing entries, the write "succeeds" but stores plain strings into a field the rest of the app now treats as `{"value","source"}` dicts. The next scrape for that item calls `item.expected_values_for_source(...)` (`tracking/scrape.py:633`), which does `entry["source"]` per entry — a plain string there raises `TypeError: string indices must be integers`, uncaught by the surrounding fetch error handling, breaking that item-source's scrape rather than just failing gracefully.
- Root cause: `_resolve_suggestion_subsets` resolves each suggestion's qualifying item subset but discards the vendor (`source_key`) before handing values to `_apply_bulk_edit_to_item` — exactly the provenance the landed model now requires each stored entry to carry.

`test_bulk_item_editing.py`'s `VendorScopedSuggestionTests` don't catch this: they assert against flat-string results (e.g. `assertEqual(item.expected_product_line, ["Gadgets"])`) and pass only because the test items involved start with empty `expected_*` lists, which masks the `dict.fromkeys` crash path and leaves the silent-corruption path unasserted.

**Fixed (tasks 5.6 and 8.8, 2026-08-22):** `_resolve_suggestion_subsets`/`_apply_bulk_edit_to_item` now carry `(source_key, value)` through to apply time and merge into each item's existing list as `{"value","source"}` dicts via a new `_merge_expected_entries` helper, deduplicated by exact `(value, source)` pair — mirroring `_merge_checked_and_manual` in the single-item form. `VendorScopedSuggestionTests` were updated to seed and assert dict-shaped entries (matching real post-migration data), plus a new regression test covering an item that already carries a vendor-tagged entry before the apply round. Full `tracking` suite (488 tests) passes.

The rest of this section is the original pre-landing analysis, kept for context on *why* the rework was anticipated and what it was expected to fix beyond bulk-edit's own apply path.

**Sections 4–5 (vendor-scoped `expected_product_line`/`expected_category` suggestions and their apply logic) are complete and correct against the current storage model, but that storage model itself is scheduled to change.** Post-implementation exploration (`/opsx:explore`, prior to archiving this change) surfaced that `SearchableItem.expected_product_line`/`expected_category` — inherited unchanged from `item-category-relevance-filter` — store a flat `list[str]`, deduplicated by exact string equality across vendors at save time (that archived change's Decision 2/Decision 9). Two consequences fell out of that, both inherited rather than introduced here:

- The single-item edit form's vendor-labeled suggestion checkboxes (`item-category-relevance-filter` Decision 9) can silently misrepresent state: if two vendors both observe the same raw string, both checkboxes pre-check regardless of which one(s) the operator actually intended, and unchecking only one of the two is a no-op — the other checkbox, sharing the same underlying stored string, keeps the value present. This is a latent bug in the archived capability, not something this change caused, but it blocks a clean fix here too.
- Because storage never retained *which vendor* an operator claimed a value through, this change's vendor-scoped suggestion apply (Decision 5; tasks 4.1–4.3, 5.5) can only gate on live `ObservedCategoryValue` vendor membership at apply time — it has no way to represent "remove this value, but only the claim that came from vendor X" cleanly. That gap is what blocked adding a symmetric remove control alongside the existing additive-only suggestions when it was explored.

**Planned fix (separate, not-yet-proposed change):** move `expected_product_line`/`expected_category` from `list[str]` to `list[{"value": str, "source": str | None}]`, so each entry carries real provenance — `source: null` for manually-typed values, rendered inline alongside vendor-sourced rows (not a separate textarea) with a fixed "Manual entry" signpost, in both the single-item (`edit_term`) and bulk-edit forms. Matching (`tracking/parsers.py`) is unaffected by this — `JSONSearchParser.add_result` only ever needs the flat set of `.value`s, handed off from `tracking/scrape.py:633-634` — so this is a storage/form-layer change, not a matching-engine change; the "an item's category identity doesn't vary by vendor" matching semantics (Decision 1) are preserved exactly.

**Migration approach (agreed, to be detailed in that change's own design.md):** for each existing stored string, attempt a best-effort vendor match against the item's currently configured `ItemSource`s — if the string matches exactly one configured vendor's `ObservedCategoryValue` (same `field_name`, exact value equality), tag the migrated entry with that vendor; if it matches zero or more than one, degrade to `source: null`. Item and vendor counts are small enough in production that an `O(items × values × sources)` migration is acceptable.

**This change is not blocked on that rework to ship or archive as specced** — Sections 4–5 are fully implemented and tested against the current (flat-string) storage model. But their vendor-scoped suggestion UI and apply logic should be revisited once the storage-model change lands: "Active on X items"-style add/remove/unchanged controls per suggestion only become clean and unambiguous once storage identity matches `(vendor, value)` pairs directly. Tracked here as a forward dependency for whoever picks up bulk-edit's `expected_*` UX next.
