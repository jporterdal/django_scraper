## Why

`search-term-relevance-filter` closes the gap where a vendor row shares words with the search term but isn't the term as a contiguous phrase (e.g. `"Dragon Fire"` for a `"Fire Dragon"` search). It cannot close a distinct gap: a row whose title **is** a legitimate phrase match for the term but is still the wrong item, because the same name exists in an unrelated category or product line — e.g. searching `"Energy Retrieval"` can legitimately return both the MTG card and the Pokémon TCG card of that exact name from a single vendor. No amount of title-phrase strictness distinguishes these, because the title text itself is identical or near-identical; only a category-level signal can. This app is not TCG-specific (vendors span card singles, LEGO sets, coffee, computer parts), so the same collision risk generalizes to any vendor where one title string is reused across unrelated product lines.

Investigation confirms the raw signal to make this distinction already exists in every in-scope vendor's response, unused: `wt` returns `row["category"]` (e.g. `"Magic the Gathering Singles"`), `f2f` returns `src["General_Game_Type"]` (e.g. `["Magic: The Gathering"]`), and `hfx` returns `product["vendor"]` (e.g. `"Magic: The Gathering"`) — none of which are currently read for filtering purposes.

## What Changes

- Add two new, independently opt-in, **list-valued**, plain-text fields on `SearchableItem`: `expected_product_line` (e.g. `["Magic"]`, or `["Magic", "MTG"]` when vendors spell the same product line differently) disambiguating same-named items across unrelated game/product lines, and `expected_category` (e.g. one or more specific MTG set names) narrowing to a specific set/printing. Each field holds zero or more plain-text values, OR-matched against the row's signal — a row passes a field's check if *any* listed value matches, so one item's setting can cover vendors that use genuinely different vocabulary for the same product line (e.g. `wt` says `"Magic the Gathering Singles"`, a hypothetical other vendor says `"MTG"` — no single substring covers both). Either field, both, or neither may be set per item.
- Add two shared checks on `JSONSearchParser` (assumes `search-term-relevance-filter` has landed and its `add_result` gate already exists) that, when an item has a non-empty `expected_product_line` and/or `expected_category` list, reject a candidate row unless the corresponding per-row signal contains **at least one** listed value as a normalized (case-folded, whitespace-collapsed) substring match — implemented as an internally regex-escaped comparison so the user never writes or sees regex syntax, unlike the existing raw-regex `title_include_patterns`. Matching is OR *within* a field's list of values, and AND *between* the two fields when both are non-empty.
- Wire `WtFiltersParser`, `ShopifyParser`, and `StorepassParser` to supply their vendor's raw product-line signal into the new check — same scope boundary as `search-term-relevance-filter` (`JSONSearchParser` subclasses only; `CCSearchParser`/`cc` and not-yet-implemented parsers such as `mastermind`/`javablend` are out of scope, left as future follow-ups). The category signal these parsers already extract today is reused unchanged for the `expected_category` check — no new per-parser extraction needed for that half.
- Add a new `product_line` column to `SearchResult`, persisted alongside the existing `category` column and displayed in `searchableitem_detail.html` and CSV/JSON export — the existing `category` field/column's meaning and display behavior are unchanged by this proposal.
- Leave a blank expected value as a full opt-out for that field — each check is skipped independently, same posture as `title_include_patterns` and the sibling change's blank-term rule.
- Rejected rows are dropped silently (DEBUG-level log only), matching the sibling change's enforcement posture at the same `add_result` choke point — not surfaced as a parse failure, not merely flagged/advisory.
- Add a vendor-scoped value-discovery UI on the `SearchableItem` create/edit form: for each of `expected_product_line`/`expected_category`, one checkbox per `(source, value)` pair observed for the item's own configured vendors, each labeled with its source (e.g. `"wt: Magic the Gathering Singles"`) so an operator can tell which vendor a suggestion came from — an HTML `<datalist>` was considered and rejected because browsers do not render `<option label>` for text-input datalists, so a plain datalist cannot show which vendor a suggestion belongs to. A free-text textarea (one value per line) sits alongside the checkboxes for values not in the suggestion list. Checked suggestions and manually typed lines are merged and exact-string-deduplicated into the stored list on save; the checkbox *choices* themselves are **not** deduplicated across vendors (a value shared by two vendors still gets two checkboxes, one per source), so re-editing an item pre-checks every checkbox whose value matches a stored entry — including cases where one stored value is simultaneously "claimed" by multiple vendors' checkboxes. Suggestions are sourced from a new, dedicated observation log (`ObservedCategoryValue`), not from `SearchResult`: every row a parser processes is recorded there regardless of whether it's ultimately accepted or rejected, so the suggestion list keeps surfacing real collisions (e.g. a same-titled Lorcana row) even as `expected_product_line`/`expected_category` filtering on other items starts suppressing those rows from ever reaching `SearchResult`. Suggestions remain non-binding — the manual textarea accepts any plain-text value regardless of whether it's suggested.
- **Design fork resolved:** the per-row product-line signal is carried by a new, distinct field/column (`product_line`), not by reusing the existing `category` field — the existing `category` field keeps its current "set/printing" meaning and display behavior for `wt`/`f2f`/`hfx` undisturbed. See `design.md` Decision 6.

## Capabilities

### New Capabilities
- `item-category-relevance`: opt-in, item-level requirement that a search result row must match at least one of the item's specified `expected_product_line` values and/or at least one of its `expected_category` values (plain-text, normalized substring, OR within a field, AND between fields) before being surfaced as a candidate, implemented on the shared `JSONSearchParser` base class and inherited by vendor-specific parsers, with the matched `product_line` persisted and a vendor-labeled checkbox suggestion UI to aid value selection across vendors with divergent vocabulary.

### Modified Capabilities
(none — this is a new, independent filtering stage layered on top of, not altering, the requirements added by `search-term-relevance-filter`)

## Impact

- `tracking/models.py`: `SearchableItem` (new `expected_product_line` and `expected_category` list-valued (JSON) fields, mirroring the existing `ItemSource.title_include_patterns`/`title_exclude_patterns` convention), `SearchResult` (new `product_line` column — still a single per-row value, unaffected by the list-vs-single-value shape of the `SearchableItem` fields), new `ObservedCategoryValue` model (`source`, `field_name`, `value`, `last_seen`) plus a one-time data migration backfilling it for `category` from historical `SearchResult` data.
- `tracking/parsers.py`: `JSONSearchParser` (new shared product-line-check and category-check methods/hooks on `add_result`, checking a row's single per-row signal against the item's *list* of expected values with OR semantics, building on the gate from `search-term-relevance-filter`; new unconditional `ObservedCategoryValue` upsert for every row processed, independent of filtering outcome), `WtFiltersParser`, `ShopifyParser`, `StorepassParser` (wired to additionally supply their vendor's raw product-line signal; existing category-signal extraction is reused unchanged).
- `tracking/forms.py` and item create/edit templates: new list-valued fields, plus a vendor-labeled checkbox suggestion UI (one checkbox per `(source, value)` pair, not deduplicated across vendors) and a manual free-text textarea, sourced from `ObservedCategoryValue`, merged and exact-string-deduplicated into the stored list on save.
- `tracking/views.py` (`EXPORT_FIELDNAMES`) and `searchableitem_detail.html`: expose the new `product_line` column alongside the existing `category` display.
- `tracking/tests/test_wtfilters_parser.py` and equivalent f2f/hfx parser tests: new same-title-different-product-line and same-product-line-different-category rejection cases.
- `tracking/fixtures/html/{wt,f2f,hfx}/search_results_sample.json`: needs added rows representing a same-title, different-product-line false positive and a same-product-line, different-category case, since current fixtures are single-category (`"Lightning Bolt"`, all MTG).
- `tracking/docs/hfx_investigation.md`: needs a callout distinguishing the existing `product_line` Storepass query parameter (request-side) from this change's `product_line` field/column (response-side) — same name, different layer.
- Depends on: `search-term-relevance-filter` (must be implemented first; this change assumes its `add_result` gate already exists and does not re-implement or alter it).
- Not affected: `tracking/matching.py`, `ItemSource.title_include_patterns`/`title_exclude_patterns`, `CCSearchParser` (HTML-based, out of scope, same boundary as the sibling change), `mastermind`/`javablend` (no parser class implemented yet).
